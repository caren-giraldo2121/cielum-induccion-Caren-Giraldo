## Autoinvestigación básica
1. Pregunta: ¿Qué es un sistema de control de versiones y por qué Git es "distribuido"?

 Respuesta (con mis palabras): Es una herramienta que permite guardar y controlar los cambios de un proyecto. Git es distribuido por que cada desarrollador que este trabajando en un proyecto tine una copia del repositorio, la cual puede clonarla trabajar en ella y guardar cambios.

 Ejemplo propio: En la universidad hice un proyecto, cada uno trabajaba en su rama, luego las uniamos y por ultimo clonabamos la rama main con todas las partes incorporadas.

Fuente: Chacon, S. y Straub, B. (s. f.). Pro Git. Git SCM. Recuperado el 30 de septiembre de 2026, de https://git-scm.com/book/es/v2

2. Pregunta: ¿Qué diferencia hay entre working directory, staging area y repositorio?
working directory es el proyecto donde estas trabajando y se hacen los cambios de un archivo, staging area es donde preparas un cambio para guardarlo y repositorio es donde guardas definitivamente un cambio que hayas hecho.

Ejemplo propio: En mi proyecto helpify tenia una carpeta llamada entidades y una subcarpeta usuarios. si modificaba usuario, ese cambio esta en mi working directory. Luego se pasaban al staging area y finalmente hacia un commit para guardarlo en el repositorio. 

Fuente: Chacon, S. y Straub, B. (s. f.). Pro Git: Los fundamentos de Git. Git SCM. Recuperado el 30 de septiembre de 2026, de https://git-scm.com/book/es/v2/Empezando-Fundamentos-de-Git

3. Pregunta: ¿Para qué sirven git init, clone, status, add, commit, log, diff, push, pull?

git init: Crea un repositorio Git vacío en una carpeta local.

git clone: Nos permite descargar una copia completa de un repositorio remoto en tu computadora.

git status: Indica qué archivos han sido modificados, cuáles están listos para el commit (staged) y cuáles aún no son rastreados por Git.

git add: Pasa los archivos del directorio de trabajo al staged.

git commit: Guarda de forma permanente los cambios que estaban en el staged en el repositorio local.

git log: Muestra el historial de commits del repositorio.

git diff: Muestra las diferencias de código (líneas añadidas/borradas) antes de agregarlas o guardarlas.

git push: Sube tus commits locales al repositorio remoto.

git pull: Descarga y fusiona los cambios del repositorio remoto en tu rama local.

Ejemplo propio: En proyectos de la universidad se creaba el repositorio, lo clonábamos y ya cada uno trabajaba desde su rama. A medida que se avanzaba, mirábamos los archivos modificados, los agregábamos al staged y hacíamos commit; seguido a esto, hacíamos push para subirlos a la rama remota del repositorio.

Fuente: Chacon, S., & Straub, B. (2014). Pro Git (2.ª ed.). Apress. https://git-scm.com/book/es/v2

4. Pregunta: ¿Qué es un remoto y qué es origin?
Un remoto es una versión del repositorio alojada en un servidor en la red, como lo es GitHub, y origin es como un apodo corto que Git asigna para que, cuando hagas un push o pull, no tengas que escribir la dirección URL completa, sino simplemente origin.

Ejemplo propio: Cuando haces push desde la terminal escribes (git push origin main).

5. Pregunta: ¿Para qué sirve .gitignore? Da 5 ejemplos de qué NO se debe subir.


.gitignore sirve para indicarle a Git qué archivos o carpetas ignorar y no rastrear.


5 ejemplos de lo que no se debe subir son:

Dependencias de paquetes: Carpetas como node_modules/ o vendor/.

Variables de entorno y credenciales: Archivos .env que contienen contraseñas o llaves API.

Archivos del sistema operativo: Archivos temporales ocultos como .DS_Store o Thumbs.db.

Archivos compilados o binarios: Carpetas como dist/, build/ o archivos ejecutables.

Configuraciones de editores: Carpetas como .vscode/ o .idea/.

Fuente: Chacon, S., & Straub, B. (2014). Pro Git (2.ª ed.). Apress. https://git-scm.com/book/es/v2 


## Autoinvestigación avanzada
1. ¿Qué es Conventional Commits y por qué ayuda en equipo?

Conventional Commits es una convención sencilla que se basa en los mensajes de confirmación para registrar modificaciones en Git, estableciendo una estructura organizada en los textos de confirmación que simplifica y clarifica la explicación de las modificaciones hechas en el proyecto.

Los Conventional Commits ayudan al equipo porque fomentan la colaboración al facilitar la revisión de los cambios realizados en el código por otros miembros, mejoran la comunicación y reducen la posibilidad de malentendidos. 



2. ¿Cómo se configura una llave SSH para GitHub y por qué es mejor que usuario/contraseña?

El uso de llaves SSH supera al método tradicional de usuario y contraseña principalmente porque ofrece una mayor seguridad al basarse en un sistema de claves criptográficas, tanto pública como privada, lo que evita por completo que las credenciales viajen por la red o se expongan en texto plano. Asimismo, destaca por su comodidad operativa, ya que una vez completada la configuración inicial, permite autenticarse de forma transparente y automática sin la necesidad de escribir contraseñas ni lidiar constantemente con tokens de acceso personal cada vez que se ejecutan operaciones esenciales en el repositorio como un push o un pull.

- Abra Terminal.   

- Pegue el texto siguiente y reemplace el correo electrónico usado en el ejemplo por su GitHub dirección de correo electrónico.
ssh-keygen -t ed25519 -C "your_email@example.com"   

- Nota: Si usas un sistema heredado que no admite el algoritmo Ed25519, usa: ssh-keygen -t rsa -b 4096 -C "your_email@example.com". Esto crea una llave SSH utilizando el correo electrónico proporcionado como etiqueta.   

- Cuando se te pida: "Introduce un archivo en el que se pueda guardar la clave", teclea Enter para aceptar la ubicación de archivo predeterminada.

- Cuando se le pida, escriba una frase de contraseña segura.

- Inicia el agente SSH en segundo plano:
eval "$(ssh-agent -s)"


3. ¿Qué es git config --global y qué debe tener configurado un desarrollador?

El comando git config --global se emplea para definir configuraciones a nivel de usuario en el entorno local, permitiendo que los parámetros establecidos apliquen de forma predeterminada a todos los repositorios del sistema operativo sin necesidad de redefinirlos en cada proyecto nuevo.

- El nombre de usuario: Define el nombre que aparecerá en el registro de tus cambios (commits).

Comando: git config --global user.name "Tu Nombre"

- El correo electrónico: Vincula tus correos de trabajo o personales con los commits realizados (idealmente el mismo correo asociado a tu cuenta de GitHub).

Comando: git config --global user.email "tu_correo@example.com"
